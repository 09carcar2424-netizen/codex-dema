# BOSS SiteOps — Safe Architecture Roadmap

> 문서 목적: BOSS SiteOps 플랫폼의 단계별 시스템 설계 원칙과 운영 기준을 정의합니다.
> 이 문서는 내부 운영팀, 개발팀, 감사 목적으로 사용됩니다.
> 최종 수정: 2026-05-12 | 버전: v1.1

---

## 설계 원칙

### 1. PostgreSQL 단일 소스
- 모든 사이트 메타데이터, 고객 정보, 운영 상태는 PostgreSQL에만 씁니다.
- Google Sheets는 읽기 전용 뷰어 및 비상 export 수단으로만 사용합니다.
- GS에 직접 쓰는 N8N 노드는 단계적으로 PostgreSQL API 호출로 교체합니다.

### 2. N8N은 오케스트레이터 전용
- N8N은 "언제 실행할지"만 결정합니다.
- "무엇을 어떻게"는 내부 API 또는 AI 레이어가 결정합니다.
- 비즈니스 로직이 N8N 노드 안에 하드코딩되면 100개 이상 운영 시 유지보수 불가능합니다.

### 3. Cloudflare는 보안 경계
- 목적: SSL 종료, WAF, DDoS 방어, 접근 제어.
- 모든 도메인의 오리진 서버 IP는 Cloudflare 뒤에 유지합니다.

### 4. 멀티사이트 인프라 분리
- 목적: 고객별 장애 격리, 백업 독립성, 법적 책임 분리.
- 단일 서버에 고객 사이트가 과도하게 집중되지 않도록 하며, 서버 1대 장애 시 영향 범위를 사전에 정의한 한도 내로 제한합니다.
- 고객 소유 사이트와 내부 운영 사이트는 서버 레벨에서 단계적으로 분리하며, 우선순위는 고객 중요도와 백업 구조에 따라 결정합니다.

### 5. 자격증명 보안
- 평문 비밀번호, API 키, 앱 패스워드를 Google Sheets에 저장하지 않습니다.
- N8N Credential Manager 또는 별도 Vault를 사용합니다.
- Claude API 키, AdSense 토큰은 프론트엔드 코드에 절대 노출하지 않습니다.
- AdSense 데이터는 고객 제공 리포트, 고객 승인 OAuth, 또는 수동 입력만 허용합니다. 고객 비밀번호 수집은 금지합니다.

### 6. 파트너 링크 정책 준수
- 고객 사이트 간 링크는 자연스러운 편집 판단 기준으로만 구성합니다.
- 링크 정책 감사 기능은 검색엔진 정책 준수 여부를 확인하기 위한 목적입니다.
- 기계적 상호 링크는 허용하지 않습니다.

## Phase 1: 68개 내부 운영 MVP 안정화

**목표**: 현재 운영 중인 68개 사이트의 자동화 파이프라인을 안정화하고 보안 기준을 충족합니다.

### 완료 기준
- [ ] WP 사이트 자동 설정 워크플로우 안정 운영
- [ ] 콘텐츠 발행 워크플로우 한/영 분기 정확 동작
- [ ] wp_app_password N8N Credential Manager 이전 (GS 평문 제거)
- [ ] SiteOps UI 검색/필터/페이지네이션 (실제 API 데이터 기준 재구현)
- [ ] 에러 센터 MVP: WP-CLI 실패 로그 수집 및 알림
- [ ] 고객/내부 사이트 서버 분리 계획 수립 (우선순위 기반 단계 실행)

### 아키텍처
```text
[Cloudflare] -> [WordPress 사이트 68개]
                        ↕
[N8N 오케스트레이터] <-> [Claude API / Ollama]
                        ↕
[PostgreSQL] <-> [Google Sheets (읽기 전용)]
                        ↕
[SiteOps Admin] / [Telegram 알림]
```

### 금지 항목
- GS에 wp_app_password, API 키 평문 저장
- 고객 사이트가 단일 서버에 과도하게 집중되는 구조 유지
- N8N 노드 내 하드코딩된 비즈니스 로직
- 홈페이지 콘텐츠 API 결과를 `$json`으로 직접 참조 (노드명 명시 필수)
- 고객 AdSense 비밀번호 수집

## Phase 2: 100~300개 멀티사이트 운영 자동화

**목표**: PostgreSQL 단독 전환, 콘텐츠 파이프라인 완전 자동화, 고객 포털 운영 시작.

### 완료 기준
- [ ] PostgreSQL 단독 전환 완료 (GS 쓰기 노드 0개)
- [ ] GS는 비상 export, 읽기 전용 리포트 용도로만 잔존
- [ ] 내부 API 레이어 구축 (N8N -> API 호출 구조)
- [ ] 링크 정책 감사 도구 (고객 사이트 간 링크 현황 시각화, 정책 준수 확인)
- [ ] Wordfriends 고객 포털 운영 (계약, 보고서, 상태 확인)
- [ ] 운영 모니터링 대시보드 (에러율, 발행량, 수익 현황)
- [ ] 서버 분리 완료: 고객 사이트 / 내부 사이트 / 관리 서버 물리적 분리
- [ ] Cloudflare Access로 SiteOps Admin 접근 제어
- [ ] 감사 로그 전체 기록 체계 구축

### 아키텍처 변경점
```text
[기존] N8N -> GS 직접 쓰기
[변경] N8N -> 내부 API -> PostgreSQL

[기존] 단일 N8N 인스턴스
[변경] 역할별 분리: 콘텐츠 / 설정 / 모니터링

[신규] 링크 정책 감사 도구
  목적: 고객 사이트 간 링크 현황 투명하게 기록
  방향: 검색엔진 정책 위반 여부 사전 확인
```

### 추가 금지 항목
- 고객에게 검색엔진 순위 상승 보장
- 기계적 상호 링크 구조 자동 생성
- 운영 로그 없는 자동 발행
- YMYL 카테고리 사이트에 대한 AI 자동 발행 (비검수 상태)

## Phase 3: 300개 이상 모니터링·권한·장애 격리 고도화

**목표**: 개입 없이 안정 운영 가능한 수준의 자동화와 감사 체계 완성.

### 완료 기준
- [ ] Google Sheets 운영 의존성 0 (비상 export 또는 읽기 전용 리포트는 허용)
- [ ] PostgreSQL Primary + Read Replica 구성 (고가용성)
- [ ] Watchdog 에이전트: 이상 감지 -> 1차 자동 복구 -> 알림
- [ ] 역할별 접근 권한 (운영팀 / 개발팀 / 고객 / 감사)
- [ ] 비용 최적화: Claude API(고품질) vs Ollama(대량) 자동 분기
- [ ] 장애 격리 보장: 서버 1대 장애 시 영향 범위를 사전 정의한 한도 내로 제한
- [ ] 운영 감사 로그 전체 기록 (누가, 언제, 무엇을)

### 아키텍처
```text
[Cloudflare WAF + Access] -> [WordPress 300+개 / 서버 분산]
                                      ↕
[N8N 멀티인스턴스] <-> [Claude API + Ollama 로컬]
                                      ↕
[PostgreSQL Primary] <-> [Read Replica]
                                      ↕
[SiteOps Admin (권한분리)] / [Wordfriends 포털] / [Watchdog 대시보드]
```

## 금지 설계 (전 단계 공통)

| 금지 항목 | 이유 |
|---|---|
| 평문 비밀번호/API키 Google Sheets 저장 | 보안 사고 시 전체 노출 |
| Claude API 키 프론트엔드 코드 노출 | 키 탈취 및 과금 리스크 |
| Google Sheets를 쓰기 주체로 유지 | 데이터 불일치, 확장 불가 |
| 고객에게 검색엔진 순위 보장 | 법적 책임, 정책 위반 |
| 기계적 상호 링크 자동 생성 | 검색엔진 정책 위반 |
| 운영 로그 없는 자동 실행 | 감사 불가, 장애 추적 불가 |
| 고객 사이트 단일 서버 과집중 | 장애 전파, 격리 불가 |
| N8N 노드에 비즈니스 로직 하드코딩 | 100개 이상에서 유지보수 불가 |
| 고객 AdSense/Google 비밀번호 수집 | 개인정보 보호 위반, 보안 사고 리스크 |
| YMYL 사이트 비검수 AI 자동 발행 | 콘텐츠 신뢰성 및 법적 책임 |

## 데이터 소유권 정의

모든 사이트 운영에 앞서 아래 소유 주체를 계약서 및 시스템에 명확히 기록합니다.

| 자산 | 소유 주체 | 비고 |
|---|---|---|
| 도메인 | 고객 또는 BOSS | 계약 시 명시 |
| WordPress 계정 | 고객 | 고객에게 관리자 권한 부여 |
| AdSense 계정 | 고객 | 고객 명의, BOSS 비밀번호 접근 불가 |
| 콘텐츠 저작권 | 계약 시 명시 | 기본: 고객 소유 |
| 서버/인프라 | BOSS | 운영 책임 BOSS |
| 백업 데이터 | 고객 | 요청 시 즉시 제공 의무 |

## 백업 기준

| 대상 | 주기 | 보존 기간 | RPO | RTO |
|---|---|---|---|---|
| WordPress 파일 | 일 1회 | 30일 | 24시간 | 4시간 |
| WordPress DB | 일 1회 | 30일 | 24시간 | 4시간 |
| PostgreSQL | 일 1회 + 실시간 WAL | 90일 | 1시간 | 2시간 |
| N8N 워크플로우 | 변경 시 | 무기한 | - | 수동 복구 |
| 자격증명 Vault | 변경 시 암호화 백업 | 무기한 | - | 1시간 |

- RPO: 데이터 손실 허용 최대 시간
- RTO: 서비스 복구 목표 시간

## 감사 로그 기준

모든 운영 행위는 아래 항목을 포함하여 기록합니다.

```text
- 실행 주체: 운영자 ID 또는 N8N 워크플로우 ID
- 실행 시각: UTC 기준 타임스탬프
- 대상 사이트: domain, site_key
- 실행 명령: WP-CLI 명령, API 엔드포인트, 발행 콘텐츠 ID
- 결과: 성공 / 실패 / 오류 메시지
- 환경: 서버 IP, N8N 인스턴스 ID
```

- 감사 로그는 최소 1년 보존합니다.
- 로그 삭제 또는 수정은 관리자 2인 이상 승인이 필요합니다.
- 고객 요청 시 해당 사이트 관련 로그를 제공합니다.

## 비밀키 교체 기준

| 자격증명 유형 | 정기 교체 주기 | 즉시 교체 조건 |
|---|---|---|
| Claude API 키 | 6개월 | 노출 의심, 비정상 과금 감지 |
| WP 앱패스워드 | 12개월 | 직원 퇴사, 노출 의심 |
| Google OAuth refresh token | 만료 시 자동 갱신 | 권한 범위 변경, 노출 의심 |
| N8N Credential | 6개월 | 노출 의심, 워크플로우 오류 |
| 서버 SSH 키 | 12개월 | 직원 퇴사, 노출 의심 |
| PostgreSQL 비밀번호 | 6개월 | 노출 의심 |

노출 의심 시 즉시 폐기 후 재발급을 원칙으로 하며, 교체 이력은 감사 로그에 기록합니다.

## 고객 포털 정책 (Wordfriends)

**동의 이력 관리**
- 서비스 이용약관, 개인정보처리방침, 리스크 고지 동의를 버전별로 저장합니다.
- 약관 변경 시 고객에게 사전 통지하고 재동의를 받습니다.
- 동의 이력(버전, 일시, IP)을 데이터베이스에 영구 보존합니다.

**고객 정보 보호**
- 고객 비밀번호는 bcrypt 이상의 알고리즘으로 해시 저장합니다.
- 고객 사이트 정보는 해당 고객만 열람 가능하도록 접근 제어합니다.
- 고객 요청 시 30일 이내 모든 개인정보 삭제 또는 제공 의무가 있습니다.

**리스크 고지 의무**
- SEO 결과, 트래픽, 수익은 보장하지 않으며 이를 계약서와 포털에 명시합니다.
- AI 자동 발행 콘텐츠 사용 사실을 고객에게 고지합니다.
- 검색엔진 정책 변경으로 인한 영향은 BOSS의 책임 범위 외임을 명시합니다.
